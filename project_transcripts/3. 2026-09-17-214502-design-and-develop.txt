     Context

     The architecture directory now documents a settled module/tier design
     (architecture/architecture.md, architecture/tech-stack.md) satisfying
     specs/001-rag-generator-requirements.md, but no code exists yet under
     project/ — the repo currently holds only planning artifacts. Before any
     implementation starts, the user wants a single master plan that lays out
     the phases of development in dependency order (which tier/module gets built
     before which, and why), without prescribing the technical details of each
     phase — those will go into their own per-phase spec files later, created
     just before that phase begins.

     This plan's only deliverable is that master roadmap file, per CLAUDE.md's
     documentation rules (specs directory, serial-numbered filename).

     Deliverable

     Create specs/002-master-development-plan.md (numbering continues after the
     existing specs/001-rag-generator-requirements.md; the empty
     specs/rag-assessment.md placeholder is left untouched — out of scope for
     this task).

     The file states up front that it defines phases only — order and scope —
     and that each phase gets its own detailed spec file
     (specs/00X-<phase-name>.md) before work on it begins.

     Phase Ordering (derived from the dependency graph in architecture.md)

     1. Project Scaffolding & Environment Setup — Create the project/backend,
        project/storage, project/frontend tier directories per the
        architecture's tier mapping; wire up env/secrets loading (.env per
        CLAUDE.md rule 7); set up dependency manifests and base automated-test
        scaffolding (backend + frontend) so every later phase has a place to add
        code and tests immediately. No dependencies — first phase.
     2. Storage Tier — Vector Store Foundation — Implement the VectorStore
        interface and its Chroma-backed implementation (upsert/query/delete with
        metadata filtering). This is the persistence foundation every backend
        data-touching service depends on. Depends on Phase 1.
     3. Backend — Ingestion Pipeline Internals — Build the Document Loaders
        (Strategy pattern, one per format: PDF/Word/Text/Markdown), Chunking,
        and the Embedding Service (Gemini wrapper). These are the pipeline
        stages that turn a raw file into vectors once wired to storage. Depends
        on Phase 2 (writes vectors into the VectorStore).
     4. Backend — Document & Set Management + Ingestion API — Build the Document
        & Set Management Service (create/list/delete sets and documents,
        ingestion status tracking) and the Ingestion Service that orchestrates
        Loader → Chunking → Embedding → VectorStore; expose both through the
        FastAPI API layer. This completes the ingestion vertical slice
        end-to-end. Depends on Phase 3.
     5. Backend — Retrieval & Generation Services — Build the Retrieval Service
        (similarity search against the VectorStore, optional set scoping) and
        the Generation Service (Groq LLM wrapper), independently of each other.
        Depends on Phase 2; exercising retrieval meaningfully also wants
        ingested data from Phase 4.
     6. Backend — Conversation Service, RAG Orchestrator & Query API — Build the
        Conversation Service (in-memory multi-turn history) and the RAG
        Orchestrator tying Conversation, Retrieval, and Generation together;
        expose it through the FastAPI query endpoint. Completes the
        question-answering vertical slice end-to-end. Depends on Phase 5.
     7. Frontend — API Client & Set/Document Manager UI — Build the API Client
        (the frontend's sole HTTP bridge to the backend) and the Set & Document
        Manager UI (create/select sets, upload documents, show status, remove
        documents), wired to the Phase 4 endpoints. Depends on Phase 4 (and
        Phase 1 for frontend scaffolding).
     8. Frontend — Chat UI & Session State — Build the Chat UI (question input,
        answer + citations display, explicit "not found in documents" state) and
        Session State handling, wired to the Phase 6 query endpoint. Completes
        the full user-facing product. Depends on Phase 6 and Phase 7.
     9. Integration & Hardening — Cross-tier end-to-end verification of both
        vertical slices (ingestion and Q&A) through the real UI, plus a pass
        against the non-functional requirements in specs/001 (reliability, error
        clarity, privacy/retention, etc.) before considering the MVP complete.
        Depends on Phase 8.

     Each phase's own unit tests are written as part of that phase (CLAUDE.md
     rule 6) — testing is not a separate phase.

     File Structure of the Master Plan Doc

     For each phase: a heading, a 1–2 sentence goal, its dependency on prior
     phase(s), and the tier/module names it produces (matching architecture.md
     terminology) — no library choices, class designs, or API schemas, since
     those belong in the per-phase spec files and are explicitly deferred there.

     Phase 1: Project Scaffolding & Environment Setup — Detailed Plan

     Context

     specs/002-master-development-plan.md names Phase 1 as: create the
     project/backend, project/storage, project/frontend tier directories, wire
     up env/secrets loading, set up dependency manifests, and add base test
     scaffolding — so every later phase has somewhere to add code and tests from
     day one. Nothing under project/ exists yet, and no Python tooling
     (dependency manager, test runner, Python version) has been chosen. This
     plan makes those choices, confirmed with the user this session, and
     scaffolds accordingly. Per the master plan's "Next Steps," this phase also
     gets its own permanent spec file,
     specs/003-project-scaffolding-and-environment-setup.md.

     Decisions (confirmed this session)

     - uv for dependency/environment management across all three tiers. Chosen
       over Poetry (no native multi-package workspace — would need manual path
       dependencies) and plain pip+requirements.txt (no lockfile, no workspace
       support). uv is not installed in this environment yet (uv --version → not
       found) — install it via pip install --user uv (scoped to the user, not a
       system-wide script) as the first execution step.
     - Multi-package workspace: project/backend, project/storage,
       project/frontend are each their own installable package with their own
       pyproject.toml, tied together by a root pyproject.toml uv workspace
       ([tool.uv.workspace] members = [...]). Matches the "split apart later
       without a rewrite" goal in CLAUDE.md more directly than one shared
       environment would.
     - Python 3.12, pinned via a root .python-version (system python3 here is
       3.14; uv installs and manages its own 3.12 toolchain independent of
       system Python — no conflict).
     - Dependency direction (extends the "tiers talk through interfaces"
       principle in architecture.md down to packaging): storage has zero
       dependency on backend. frontend has zero dependency on backend/storage
       code — HTTP only, via its own API Client (built in a later phase).
       backend depends on storage only for its composition root (main.py, where
       the concrete ChromaVectorStore gets constructed at startup) —
       business-logic modules (services) depend only on the VectorStore
       interface, defined in backend as a typing.Protocol so storage's
       implementation satisfies it structurally, without importing backend at
       all.
     - pytest as the test runner for all three tiers (CLAUDE.md rule 6, industry
       standard). Frontend additionally uses Streamlit's built-in
       streamlit.testing.v1.AppTest for UI smoke tests — ships with streamlit,
       no extra dependency.
     - pydantic-settings for the backend's Settings/env-var loading — idiomatic
       alongside FastAPI/pydantic (already in the stack), gives
       typed/required-vs-optional env var validation for free. Lighter
       alternative considered: python-dotenv + manual os.environ reads —
       rejected because it pushes that validation back into hand-written code.
     - Linting/formatting tooling (ruff, mypy, etc.) is out of scope for this
       phase — the master plan's Phase 1 goal is scaffolding + test harness, not
       code-quality tooling. Can be proposed later once there's real code to
       lint.
     - The subpackages named in architecture/backend-low-level-design.md
       (domain/, interfaces/, loaders/, services/, clients/, api/ under backend;
       the Chroma module under storage; ui/ under frontend) are not created
       empty in this phase. Each gets created by the phase that first adds real
       content to it (Phases 2–8), so this phase doesn't scaffold unused
       structure ahead of need.

     Concrete Hardening Fixes Found This Session

     Cross-checking specs/001's exact requirement text against the current
     design surfaced five specific, fixable gaps — not abstract categories:

     1. Empty documents silently succeed (violates A1.4's "clearly when it was 
        not [added]... empty file"). IngestionService.ingest() (Phase 4, already
        implemented) currently marks a document READY even if chunking produces
        zero chunks (e.g. an empty .txt file) — nothing is stored, but no error
        is shown. Fix: if len(chunks) == 0, treat it as a failure (mark_error,
        raise a clear error) instead of mark_ready.
     2. Ingestion failures surface as opaque 500s (violates A5.22's "plain 
        language, not technical error codes" and B4.7's "fail gracefully with a 
        clear message"). backend/api/document_routes.py's upload_document only
        special-cases SetNotFoundError; any other ingestion failure (corrupt
        PDF, the empty-file case above) bubbles to FastAPI's default 500 with no
        detail. Fix: catch ingestion failures explicitly, return 422 with a
        plain-language detail.
     3. No startup-time secrets check (relevant to B4.7 reliability). Settings()
        (pydantic-settings) is only constructed lazily on first request
        (deliberately, per Phase 4's design, so tests don't need a real .env) —
        but that means a misconfigured .env in a real deployment fails silently
        until a user's first action. Fix: a FastAPI lifespan handler that calls
        get_settings() once at startup and logs a clear warning (not a hard
        crash, so tests/TestClient usage without a .env stay unaffected) if it
        fails.
     4. No loading indicators planned for upload/ask (A4.20: "not left wondering
        if it's stuck"). Phase 7/8 plans don't currently call out st.spinner
        for the upload and ask actions. Fix: add them when those pages are
        implemented.
     5. LLM response consistency not addressed (B1.2: "same question against the
        same documents should give a consistent, dependable answer"). The Phase
        5 plan doesn't pin a temperature. Fix: GroqClient defaults to
        temperature=0 (or another low fixed value) rather than the API default,
        when it's implemented.
